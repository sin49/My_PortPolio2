# 측정 (Spatial Hash 전/후 비교 증명용) — 2026-11-19

> 상태: **측정 완료 (11/19)** — 기준선 → Spatial Hash → 칸 크기 실험 → 렌더 개선. **요약은 12장**, 원본 CSV는 `docs/measure/`

## 0. 예상 (측정 전에 적어 둠 — 맞았는지도 포폴 재료)
- 검색 1번 비용(겹침 검사 수)은 **수십~수백 배** 감소 확실 (질문마다 9999칸 → 칸 1~4개)
- FPS 개선은 **병목에 따라 다름**: 2200마리 한계의 원인이 렌더·물리면 작게 오름
- Chaser가 플레이어에게 **몰리면** 한 칸에 수백 마리 → 해시가 가장 불리한 상황. 그래서 장면 2개로 나눠 잼
- 11/19 사용자 캡처 (Debug+ASan, 튜토리얼, 1902개): FPS 16, 프레임당 5틱. 적이 발판·바닥에 줄지어 쌓여 공격 중인 적이 거의 없음 → 이 장면은 검색보다 물리·렌더가 병목일 가능성

## 1. 보이는 것 (F1 디버그 패널, 초록 줄)
- `ms/frame`: 구간별 시간 (한 프레임에 틱이 여러 번이면 합, 지수 이동 평균)
  | 구간 | 포함 |
  |---|---|
  | tick | 고정 틱 전체 |
  | ai | EnemyAI + ShooterAI + 발사 의도 → 탄 생성 |
  | physics | Motor + Physics |
  | proj | 탄 이동·벽 |
  | spatial+combat | `SpatialQuery.Rebuild` + 공격 단계 + 근접·탄 판정 (**해시로 줄어야 하는 곳**) |
  | render | 그리기 명령 제출 (`EndDrawing`의 vsync 대기는 제외 → `Render::Draw` / `Present` 분리) |
- `spatial [full scan] queries / slots / overlap checks`: 지난 틱 검색 횟수, 훑은 칸 수, 정확한 겹침 검사 수
- **F5** = 지금 값 한 줄을 실행 폴더 `stress_results.csv`에 추가 (엑셀로 열림, 빌드 종류도 기록)

## 2. 구조
- `core/Profiler_C`: `FrameProfiler` + **RAII `ProfileScope`** (만들 때 시작, 블록을 나갈 때 소멸자가 기록 = C#의 `using`). `std::chrono`만 → 테스트 가능
- `SpatialQuery`: `SpatialQueryStats` 카운터 (`mutable` = const 함수 안에서도 셀 수 있게). `Rebuild`에서 0으로
- 해시를 넣은 뒤: CSV `spatial` 열이 `full-scan` / `hash`로 갈림 + 패널에서 런타임 전환 키 (같은 장면 A/B)

## 3. 측정 절차 (Release로)
```
cmake --build build --config Release
.\build\bin\Release\Main.exe
```
1. Enter → 방 1 (튜토리얼 문 통과). 플레이어는 시작 자리에 가만히 (재현성)
2. F1 (패널 + 무적)
3. **장면 A "퍼짐"**: F4 ×N 직후 바로 F5 (막 소환 = 방 전체에 흩어짐)
4. **장면 B "몰림"**: 그대로 10초 기다린 뒤 F5 (Chaser가 플레이어 주변에 모임)
5. N = 1, 5, 10, 20 (적 100·500·1000·2000)
- 해시 완성 후 같은 절차 → 표 2개 비교 → README

## 4. 기준선 v1 결과 (11/19 사용자 측정, Release, 튜토리얼 방, 전체 순회) — 원본 `docs/measure/baseline_v1_frame-sum.csv`
> ⚠ v1은 **프레임당 합 + F5 순간값**. 느린 프레임은 틱을 여러 번 돌려서 tick ms가 부풀어 보임 → 6장(v2)에서 보강
| 엔티티 | FPS | tick ms | spatial+combat ms | render ms | 질문/틱 | 겹침 검사/틱 |
|---|---|---|---|---|---|---|
| 1,002 | 60 | 0.65 | 0.44 | 4.5 | 18 | 18,036 |
| 2,002 | 58 | 1.43 | 1.18 | 9.1 | 45 | 90,090 |
| 4,002 | 45 | 5.36 | 4.90 | 16.7 | 106 | 424,212 |
| 6,002 | 23 | 20.07 | **18.94** | 24.3 | 143 | 858,286 |
(ms = 프레임당 합. ai·physics·proj는 6,000마리에서도 합쳐 1ms 남짓)

읽은 것:
- **틱 시간의 94%가 spatial+combat** (6,002마리). 엔티티 1.5배(4k→6k)에 검색 3.9배 = **N²**: 공격 중인 적 수(질문)도 N에 비례하고, 질문마다 전체를 훑음 (겹침 검사 = 질문 × 살아 있는 수)
- render는 **N에 비례** (마리당 약 4µs). 6,000마리에서 프레임의 절반 이상
- 프레임 ≈ tick + render (43.5ms ≈ 20.1 + 24.3, 나머지는 거의 0)

## 5. 해시 후 예상 (구현 전에 적어 둠)
- 질문당 후보: 9999칸 순회 + 6,000 검사 → 칸 1~4개 안의 후보만. 플레이어 주변에 몰려도 **수십~수백**
  - spatial+combat **18.9 → 1~2ms** 예상 (+ Rebuild 때 6,000번 Insert 비용, 1ms 미만 예상)
- tick 20 → 3ms 안팎 (**약 6~10배**). 프레임이 짧아지면 프레임당 틱 수도 줄어 이득이 겹침
- **FPS는 6,000마리에서 23 → 35 안팎 (약 1.5배)**: 그다음 병목은 render 24ms (해시와 무관)
  - 다음 개선 후보 (해시 뒤 측정으로 확인): 화면 밖 적 그리기 생략(컬링), 미니맵 적 점을 원 → 사각형 (raylib 원 = 삼각형 수십 개)
- 포폴 문장 후보: "주변 검색 N² → 근처만: 로직 시간 X배 감소, 이후 병목이 렌더로 이동함을 측정으로 확인 → 컬링으로 Y"

## 6. 측정 보강 v2 (11/19) — 공정한 전/후 비교용
v1의 약점 2개를 고침:
| 약점 | 보강 |
|---|---|
| ms가 **프레임당 합** → 느린 프레임은 틱 2~3번 → 부풀어 보임. 해시로 빨라지면 틱 수도 줄어 개선이 과장됨 | **틱당 평균** (`FrameProfiler`가 구간별 호출 수도 셈). render만 프레임당 |
| F5 = **순간 1프레임** → 운이 섞임 | **3초 구간 평균** (`MeasureRecorder`): 프레임 수, 틱 수, FPS, 틱당 검색·겹침 수 |
| 사람이 키를 눌러 재현성 낮음 | **`Main.exe --bench` 자동 시나리오** (`BenchScript`, 타이머 + 상태 enum) |

`--bench` 시나리오 (해시 후에도 그대로 다시 돌림):
```
for N in [500, 1000, 2000, 3000, 4000, 5000, 6000]:
    새 게임 (튜토리얼 방, 플레이어 가만히, 디버그 모드 = 무적)
    작은 Chaser N마리 소환 (시드 고정 랜덤 위치)
    0.5초 뒤 3초 측정 -> "spread" (퍼짐: 막 소환됨)
    소환 12초 뒤 3초 측정 -> "cluster" (몰림: 플레이어 쪽에 모임)
-> bench_results.csv (실행 폴더) 후 자동 종료
```
- **벤치는 vsync 끔** → FPS가 60에 막히지 않고 실제 처리량
- CSV 열: `build, spatial, scene, room, target, entities, frames, ticks, fps, frame_ms, tick·ai·physics·projectiles·spatial_combat _ms_per_tick, render_ms_per_frame, queries·slots·overlap_checks _per_tick`
- 결과 원본은 `docs/measure/`에 보관 (README가 링크)

|---|---|---|---|---|---|---|
| 1,000 | 퍼짐 / 몰림 | 60 / 60 | 0.51 / 0.66 | 0.36 / 0.51 | 18k / 26k | (vsync) |
| 2,000 | 퍼짐 / 몰림 | 60 / 60 | 1.02 / 1.37 | 0.82 / 1.18 | 66k / 95k | (vsync) |

| 4,000 | 퍼짐 / 몰림 | 51.9 / 48.2 | 2.81 / 3.79 | 2.50 / 3.48 | 282k / 392k | 15.9 |
| 5,000 | 퍼짐 / 몰림 | 38.9 / 34.5 | 3.85 / 5.38 | 3.51 / 5.05 | 429k / 611k | 19.6 |
| 6,000 | 퍼짐 / 몰림 | 30.5 / 24.8 | 4.95 / 7.05 | 4.56 / 6.66 | 590k / 847k | 23.0 |

읽은 것:
- **v1이 부풀었던 것 확인**: v1 "6,002마리 tick 20ms"는 프레임당 합. 틱당으로는 **7.05ms** (프레임당 약 2.4틱). 보강 안 했으면 해시 효과가 과장될 뻔
- 틱 안에서 **spatial+combat = 92~95%** (6,000마리). 몰림이 퍼짐보다 1.5배 (공격 중인 적 = 질문 수가 많음)
- 프레임 = 틱 수 × 틱 시간 + render. 6,000 몰림: 2.4 × 7.05 ≈ 17ms + render 23ms ≈ 40ms → 로직 약 42%, 렌더 약 58%
- ⚠ **이 PC는 드라이버가 vsync를 강제**함 (`--bench`에서 끄도록 해도 60FPS에 막힘). 그래서 3,000 이하 render ms에는 vsync 대기가 섞임 → **render·FPS 비교는 4,000 이상만 유효**. 틱당 ms·검색 수는 CPU 로직이라 영향 없음

## 8. 해시 후 예상 수정 (v2 기준, 구현 전)
- 틱당 spatial+combat: 6.66 → **0.5ms 안팎**, 틱당 tick: 7.05 → **1ms 안팎 (5~8배)**
- 6,000마리 FPS: 프레임 ≈ render 23ms + 줄어든 로직 → **약 40 (몰림 24.8 → 약 1.6배, 퍼짐 30.5 → 약 1.3배)**
- 그다음 병목 = render (해시와 무관) → 컬링·미니맵 점 개선 후보

### 왜 로직 개선이 예상보다 작았나 (숫자로 확인한 원인)
- 질문 1번당 후보: 6,000 퍼짐 86k / 97질문 = **약 880개**. 칸 128px에 고르게 퍼졌다면 질문당 100~200개였어야 함
- 원인: **중력**. 소환 0.5초 뒤면 적이 거의 다 바닥·발판 위 → 방 높이 22칸 중 **바닥 한 줄 칸**에 몰림. 격자가 2D가 아니라 사실상 1D (가로 18칸에 6,000마리 = 칸당 약 330)
- 공격하는 적(질문)은 플레이어 주변 = 가장 빽빽한 칸 → 후보가 많은 칸만 골라서 물어보는 셈
- 남은 2.65ms에는 매 틱 Rebuild(9,999칸 순회 + 6,000번 Insert), 질문마다 후보 정렬(k log k)도 포함
- 교훈 (포폴 문장 후보): "자료구조의 이득은 **데이터 분포**가 정함. 게임은 중력 때문에 엔티티가 바닥에 몰려서, 같은 해시라도 칸 크기 선택이 중요"

### 다음 후보 (측정으로 고를 것)
1. **칸 크기 실험**: 64·32px (바닥 한 줄에 몰린 분포엔 작은 칸이 유리할 가능성). `--cell=64` 같은 옵션으로 같은 벤치
2. **render** (6,000마리 23ms/프레임 = 지금 프레임의 80% 이상): 화면 밖 적 그리기 생략, 미니맵 점 원 → 사각형

## 10. 칸 크기 실험 (11/19, `--bench --cell=N`) — `docs/measure/bench_v4_cell*.csv`
가설 (9장): 적이 바닥 한 줄에 몰렸으니 칸을 작게 하면 후보가 줄어 빨라질 것

| 칸 (px) | 6,000 퍼짐: 틱당 검색+판정 ms / 겹침 검사 | 6,000 몰림: ms / 겹침 검사 | 6,000 몰림 FPS |
|---|---|---|---|
| 32 | 4.92 / 77k | **8.47** / 139k | 21.1 (전체 순회보다 느림) |
| 64 | 1.94 / 85k | 3.22 / 153k | 35.2 |
| **128 (기본)** | **1.75** / 86k | **2.94** / 153k | **35.6** |
| 256 | 1.91 / 100k | 2.92 / 153k | 36.1 |

결과: **가설 틀림. 128 유지**
- 칸을 32로 줄여도 몰림 장면의 겹침 검사는 거의 그대로 (153k → 139k). 후보가 많은 이유는 칸이 커서가 아니라, Chaser가 **실제로 플레이어 위치에 수백 마리 겹쳐 쌓여** 있기 때문 (분리 조향이 없어서 같은 자리에 겹침). 진짜 이웃이라 어떤 칸 크기로도 못 줄임
- 작은 칸은 오히려 손해: 몸 하나가 칸 여러 개에 등록 → Insert 횟수·후보 중복·정렬 비용 증가. 32px(몸 22x28보다 작은 칸)는 전체 순회보다 느려짐
- 64~256은 비슷, 128이 퍼짐·몰림 모두 무난 → 기본값 그대로
- 포폴 문장 후보: "칸 크기는 엔티티 크기보다 커야 하고, 남은 비용은 '진짜로 겹친 적'이라 자료구조가 아니라 게임 규칙(적끼리 밀어내기)으로 풀 문제"
- 결과 동등성 테스트도 칸 크기 4종 전부로 확장 (`SpatialQueryTest_C`)

## 11. 렌더 개선 (11/19) — `docs/measure/bench_v5_render-A_minimap.csv`, `bench_v6_render-AB_minimap-cull.csv`
해시 뒤 6,000마리 몰림: 프레임 28ms 중 **render 22ms** (9장). 의심 2곳을 하나씩 적용해 측정
| 단계 | 바꾼 것 | 6,000 몰림 FPS | 근거 |
|---|---|---|---|
| (해시까지) | — | 35.6 | render 22ms |
| **A** | 미니맵 적 점: `DrawCircleV`(원) → 3x3 사각형 | **60 (vsync 상한)** | raylib 원 = 삼각형 36개. 6,000마리면 삼각형 21만 개가 미니맵에만 |
| **B** | 컬링: 화면(+48px) 밖 적·탄은 안 그림 | 60 (상한) | 6,000에선 이미 상한 → 차이 안 보임 |

- **A 하나로 6,000마리 render 22ms → 5ms 안팎** (A 단독 측정). 화면 밖 미니맵 점 하나가 렌더 비용의 대부분이었음 = 측정 없이는 의심하기 어려운 곳
- 6,000이 60FPS에 붙어서 벤치에 **8,000·9,900마리 단계 추가** (World 용량 9999 근처)
- A+B: **9,900마리 퍼짐 59.9 / 몰림 58.7 FPS**. 틱당 로직 8.05ms (몰림)
- ⚠ 한계: 60FPS 상한(드라이버 vsync 강제)에 붙으면 남는 시간을 Draw 안의 GPU 대기가 먹어서 **render ms 값 자체는 믿을 수 없음** (A·B 실행마다 5~14ms로 흔들림). 그래서 B(컬링)의 효과는 이 PC에서 **분리 측정 못 함** → FPS가 상한 아래인 구간에서만 비교 가능. README에도 그대로 적음

## 12. 전체 요약 (같은 PC, Release, 튜토리얼 방, 6,000마리 몰림 기준)
| 단계 | FPS | 틱당 로직 ms | 틱당 겹침 검사 |
|---|---|---|---|
| 기준선 (전체 순회) | 25.0 | 7.04 | 847k |
